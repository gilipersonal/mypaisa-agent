🔁 One Claude tool loop, with code doing every sum

The agent Lambda runs one tool loop on Sonnet 5.5. Before each call it reads the month's spend and lets the ladder choose the model. It sends only the current conversation after a cached prefix, loops through strict tools until it can answer, ask one thing, or show a Confirm card. A draft writes nothing: only a Confirm, a check-in's tap or a Save in place commits, through the one write service.

👥 Nine agents that never call each other

Each agent is a Lambda with its own role, tools, model routing and budget share. They publish events on the mypaisa-<env>-events EventBridge bus and leave work in DynamoDB; the daily run is one Step Functions state machine. No agent can trade, read a secret, delete data or apply infrastructure. The concierge is the agent Lambda from phase 1; the rest join it in phase 18.

🧠 Three Claude models, each where it earns its cost

Sonnet carries the conversation, Haiku files and filters at volume, Opus thinks once a week. All three go through one wrapper that meters every call from the API's own usage counts, so the cost on the span is what will be billed. Prompt caching covers the system prompt, the tool list and the card rubrics. Prices are as TECH_STACK.md records them, per million tokens in and out.

🛡️ Enforced in code, not in the prompt

Claude never produces a number

Every figure comes from tested code: XIRR, loan schedules, the Projection, the engine's pillars. Claude chooses what to say and how.

§1 rule 1 · wealth/ · the engine

The app cannot trade

No broker login and no orders. No tool can trade, spend beyond a search, delete data or message anyone but the member it answers.

§1 rule 2 · §8 guardrails

A policy gate before every tool call

Code checks the agent's manifest, the member's role and household, the arguments (an amount stays the member's own words) and the run's caps, and fails closed. Third-party text is data only; a chat that has read it loses its outbound tools, and the server tools run in a call with no household figure.

§23.2 · MA-247, MA-253

Tested on change, watched live

T0 replays on every pull request; T1 live, three trials, when a prompt, tool, guard, loop, routing, kind or the SDK changes; T2 on a model change before release. Every live run checked by code; flagged runs and 10% judged overnight; judges calibrated by the admin. The explainer.

§23.3 to §23.5 · MA-246, MA-250 to MA-255

One write service

New things are created only in the chat, with a card and a Confirm; a figure is corrected in place with Save. Both validate against the kind and write the audit row.

§4.10 · PATCH /v1/records/{id}

Admin actions take a second check

A fresh, server-verified Sign in with Apple, passkey or Google, bound to the action. A local Face ID alone never authorises anything on the server.

§4.5 · MA-76

Nothing is lost

Every hand-off is an SQS queue; handlers are idempotent; a dead letter alarms at once and replays safely. An old Confirm whose flow expired is refused.

§21 · Powertools idempotency

Nothing private in CloudWatch

No prompt, reply, amount, name, token or account number on any span, log or metric; members are hashed. A leak test replays a conversation in CI to hold the line.
