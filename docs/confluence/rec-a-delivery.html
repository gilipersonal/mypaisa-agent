17.1 Two environments, one account

Kept apart by IAM, not by trust. Each Lambda's role names only its own environment's resources. The developer's role works in dev; an explicit deny keeps it out of anything tagged env=prod, so a slip on a laptop cannot read or change the household's data. The developer role's one exception to its env=prod deny is ssm:PutParameter on /mypaisa-agent/prod/*, for Arun to put prod's secret values by hand; it never reads, decrypts, deletes or tags a prod parameter, and Claude never runs it (Arun, 24 Nov 2026, MA-26). The exception is cut out of the deny itself, since an explicit deny beats any allow; what it leaves open is that a wrong put could overwrite a prod secret (never read one), which CloudTrail records and Arun puts right by hand. Tokens from one pool are refused by the other environment's api. By default across phases 0 to 15 both environments run without custom VPCs (enable_vpc_lockdown = false, £3.50/month); an optional seven-layer VPC enterprise lockdown (mypaisa-dev-vpc 10.10.0.0/16 and mypaisa-prod-vpc 10.20.0.0/16 with zero peering, VPC Block Public Access, zero-egress Isolated subnets, free S3 and DynamoDB Gateway Endpoints with three-way aws:SourceVpce Data Perimeter Deny policies, IPv6 EIGW, and Graviton t4g.nano fck-nat/Envoy TLS-SNI egress proxies + Route 53 DNS Firewall default-deny allowlists — preferred Option 3 adding +£13.32/month in 3A or +£24.86/month in 3B with CloudFront Pro bundled AWS WAF on prod, inside §14.2's £50/month AWS cap; MA-283, MA-284, docs/RESEARCH.md §9) is decided last, after phase 15.

Local development runs the whole app on the laptop (MA-198): a moto server for DynamoDB, S3 and SQS (no Docker); the handlers behind one local ASGI app, the SSE stream included; the SvelteKit dev server; the iOS simulator pointed at localhost; and a localhost-only sign-in stub, compiled out of every deployed build. The agent runs either against the dev Claude key or in a scripted mode that replays recorded conversations, which UI work, the end-to-end tests and parity with the prototype use. Until phase 1 builds the real handlers, the stack carries stand-ins for the chat api and the stream in scripts/local/, on the wire of §19, which MA-30 and MA-31 replace. The same code also runs against dev in AWS: the MyPaisa Dev build on the simulator or a device against api-dev, the web app from localhost against api-dev, and the dev Cognito pool for sign-in.

17.3 Identity

§4.5 and §13 hold the detail. In short: one Cognito user pool per environment, Essentials plan; one user per member, with their Apple account, Google account and passkeys linked to it; Apple's and Google's identity tokens verified by custom-auth Lambda triggers; five-minute access tokens and rotating refresh tokens in the Keychain; in a browser, the session cookie on the api's host, which also opens the stream; passkeys whose relying party is the dashboard's domain; the second check a fresh, server-verified assertion; sign-out of a device or everywhere and pause through Cognito and the member's session epoch, which the open stream re-checks every 60 seconds (MA-102, §19.5). 17.4 Delivery

Terraform only. infra/modules/mypaisa holds the whole stack once but its SSM parameters; infra/dev and infra/prod call it with their own settings and keep separate state (mypaisa-agent/<env>/infra.tfstate in the existing state bucket). Every SSM parameter, secret or id, lives in infra/modules/secrets, called by infra/dev-secrets and infra/prod-secrets with state of their own (mypaisa-agent/<env>/secrets.tfstate), so the plan CI runs on a pull request never refreshes one (Arun, 24 Nov 2026, MA-25). A change is planned to a file, the plan is read, and that file is applied. Prod resources that hold data carry prevent_destroy. Secret values are put in SSM by hand, after the first apply; Terraform creates each parameter with a write-only placeholder (value_wo, §13), so no value reaches its state. The AWS MCP is for reading (describe, logs, metrics, costs) and never changes a resource (.claude/rules/aws-changes.md).

17.5 Hydrating prod: the Excel importer

Prod starts empty, and years of past investments are needed for XIRR. They come in through one versioned Excel template (MA-111), sent in the chat as a file, from the app or the web app, or uploaded into the chat by Claude Code on the owner's laptop through a one-time link (below):

  1. MyPaisa reads the workbook and checks it against the template's version: sheets, columns, types, dates, currencies, known holdings.
  2. A dry run shows what would be added, what is already there (matched by a fingerprint of each row, so sending the same file twice adds nothing) and every row it refuses, with the reason.
  3. Confirm, with the second check (MA-102), writes the rows in batches, each with its audit row, under one import id.
  4. Any import can be rolled back by its id.

The template carries the years of investment history; the budget and the plans are set up through the chat, not imported (Arun, 29 Oct 2026, MA-275). From Claude Code, through a one-time link (Arun, 29 Oct 2026, MA-275: "I still want to hydrate prod through excel, by providing it to chat using claude code", then "Claude Code uploads it"). The owner prepares the workbook with Claude Code on the laptop, then taps Upload from my laptop in the chat. The app shows a one-time link, the owner's alone: it accepts one .xlsx of at most 20 MB within 15 minutes, through the chat API's presigned upload into the documents bucket (§4.6, MA-31), and then expires. Claude Code sends the workbook to it with one command; the link carries no credential beyond that one upload, and Claude Code never signs in to the household. The file lands in the owner's chat as if the owner had sent it, with its Document row and an audit row naming the link, and the importer's dry-run card follows there. Nothing is written until the owner confirms that card in the app with the second check, exactly as for a file sent from the phone; a link used twice, late or by anyone else adds nothing. The workbook's cells are untrusted text like any file's (§21.2): parsed in code, never read as instructions. The same importer works in dev against the seeded household, so it is tested before it ever touches prod. It is built in phase 9 (MA-111), for prod's years of history. The old wealth tracker holds no real data, so nothing is mapped from it; MA-105 ports its maths instead (§11).
