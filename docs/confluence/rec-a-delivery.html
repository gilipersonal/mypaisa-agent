18.1 Two environments, one account

One AWS account (us-east-1), every component twice. Names are mypaisa-<env>-<part> and every resource carries the tag env. Nothing is shared between the two except the account, the DNS zone and the certificate.

Local development runs the whole app on the laptop (MA-198): a moto server for DynamoDB, S3 and SQS (no Docker); the handlers behind one local ASGI app, the SSE stream included; the SvelteKit dev server; the iOS simulator pointed at localhost; and a localhost-only sign-in stub, compiled out of every deployed build. Data. Dev and the laptop are seeded and hydrated with one illustrative household of every kind, in the UK and India, with years of events (salary history, EMIs paid, valuations, SIPs, statements), from the design figure set (docs/design/figures/household-v4.json) that the boards and the prototype also use. A generator writes it through the write service, and scripts/seed.sh local|dev loads it and can wipe and reseed (MA-110); that is the only way dev data is written. Prod starts empty and fills only through the app: the chat, statements, and for years of history the Excel importer (§18.5). No script writes to prod tables.

18.3 Identity

§4.5 and §14 hold the detail. In short: one Cognito user pool per environment, Essentials plan; one user per member, with their Apple account, Google account and passkeys linked to it; Apple's and Google's identity tokens verified by custom-auth Lambda triggers; five-minute access tokens and rotating refresh tokens in the Keychain; in a browser, the session cookie on the api's host, which also opens the stream; passkeys whose relying party is the dashboard's domain; the second check a fresh, server-verified assertion; sign-out of a device or everywhere and pause through Cognito and the member's session epoch, which the open stream re-checks every 60 seconds (MA-102, §21.5). Built in phase 1, so every later piece starts signed in (MA-109).

18.4 Delivery

Terraform only. infra/modules/mypaisa holds the whole stack once; infra/dev and infra/prod call it with their own settings and keep separate state (mypaisa-agent/<env>/infra.tfstate in the existing state bucket). A change is planned to a file, the plan is read, and that file is applied. Prod resources that hold data carry prevent_destroy. Secret values are put in SSM by hand, after the first apply; Terraform creates each parameter with a write-only placeholder (value_wo, §14), so no value reaches its state. The AWS MCP is for reading (describe, logs, metrics, costs) and never changes a resource (.claude/rules/aws-changes.md).

18.5 Hydrating prod: the Excel importer

Prod starts empty, and years of past investments are needed for XIRR. They come in through one versioned Excel template (MA-111), sent in the chat as a file, from the app or the web app, or uploaded into the chat by Claude Code on the owner's laptop through a one-time link (below):

  1. MyPaisa reads the workbook and checks it against the template's version: sheets, columns, types, dates, currencies, known holdings.
  2. A dry run shows what would be added, what is already there (matched by a fingerprint of each row, so sending the same file twice adds nothing) and every row it refuses, with the reason.
  3. Confirm, with the second check (MA-102), writes the rows in batches, each with its audit row, under one import id.
  4. Any import can be rolled back by its id.

The template carries the years of investment history; the budget and the plans are set up through the chat, not imported (Arun, 29 Oct 2026, MA-275). From Claude Code, through a one-time link (Arun, 29 Oct 2026, MA-275: "I still want to hydrate prod through excel, by providing it to chat using claude code", then "Claude Code uploads it"). The owner prepares the workbook with Claude Code on the laptop, then taps Upload from my laptop in the chat. The app shows a one-time link, the owner's alone: it accepts one .xlsx of at most 20 MB within 15 minutes, through the chat API's presigned upload into the documents bucket (§4.6, MA-31), and then expires. Claude Code sends the workbook to it with one command; the link carries no credential beyond that one upload, and Claude Code never signs in to the household. The file lands in the owner's chat as if the owner had sent it, with its Document row and an audit row naming the link, and the importer's dry-run card follows there. Nothing is written until the owner confirms that card in the app with the second check, exactly as for a file sent from the phone; a link used twice, late or by anyone else adds nothing. The workbook's cells are untrusted text like any file's (§23.2): parsed in code, never read as instructions. The same importer works in dev against the seeded household, so it is tested before it ever touches prod. It is built in phase 9 (MA-111), for prod's years of history. The old wealth tracker holds no real data, so nothing is mapped from it; MA-105 ports its maths instead (§12).
