4.5 Identity, members and views

Page 3: the two doors (the iOS app and the web app), Sign in with Apple, Google and a passkey, the custom auth, Cognito, the Keychain and the session cookie, the authorizer, and the owner's sign-out and pause. Open it in Lucid. There are no passwords. Apple or Google vouches for the person: Sign in with Apple on any iPhone or iPad, or Sign in with Google for a member who prefers it (Arun, 25 Oct 2026, MA-161: "No more telegram login, on Google SSO or iOS login"). "Signing in" is: which Apple or Google account is this, which member is it linked to, and which household is that member in.

One identity store, on AWS from day one (Arun, 24 Oct 2026; MA-109). Each environment has its own Amazon Cognito user pool, mypaisa-dev-users and mypaisa-prod-users (Essentials plan, free under 10,000 monthly users), with one user per member: that member's Apple account, Google account and passkeys are all linked to the same Cognito user. Password sign-in and self sign-up are off, and a user is created only when someone joins through an invite.

StepHow
The buttonsThe app shows Apple's and Google's own buttons, Apple's first, and nothing else. Sign in with Apple runs natively (ASAuthorizationAppleIDProvider, no name or email asked for); Google runs through Google's iOS SDK in the system's web sheet, with PKCE.
The tokenBefore either sheet opens, the app asks the api for a one-time nonce (/auth/nonce); Apple's identity token (carrying the nonce's SHA-256) or Google's ID token (carrying the nonce) comes back.
The exchangeThe app posts the token to /auth/apple or /auth/google. The api finds the member that provider account (sub) is linked to and starts Cognito's custom auth for them; the verify trigger checks the token against Apple's or Google's published keys: issuer, audience (the app's bundle id for Apple, the environment's Google iOS client id for Google), expiry, an issue time under five minutes, the nonce, and no replay. Cognito then issues that member's tokens.
An unknown accountAn Apple or Google account linked to no member is refused, whatever its address, unless the request comes from the app with a valid invite token, which creates the member (Joining, below; a browser never joins). A paused member gets one line and nothing else (MA-102).
In a browserThe web app (§9.4) shows the same two buttons, through Sign in with Apple's JS (the environment's Services ID as the audience) and Google Identity Services (the environment's Google web client id), and a passkey. The same /auth/apple and /auth/google exchange runs; no client secret is used. The api then sets an HttpOnly, Secure, SameSite=Strict session cookie for its own host, with five-minute access tokens behind it that page scripts never see.
A passkeyA member adds one from You in the app (MA-77). In the app it answers the second check (below), never the sign-in screen, which shows Apple and Google only; in a browser it signs in to the web app. To sign in with it, the page asks /auth/passkey/options for a one-time WebAuthn challenge, the device signs it under Face ID or Touch ID, and the assertion goes to /auth/passkey; the api starts Cognito's custom auth for the member whose credential it is, and the verify trigger checks the signature against that credential's stored public key, the challenge, the origin and the relying-party id. The relying-party id is the environment's dashboard domain (dashboard.mypaisapp.com, dashboard-dev.mypaisapp.com): it is the web app's origin and serves the iOS app's association file, whose webcredentials entry lets one passkey work in both. MA-109 confirms it before anyone registers a passkey; changing it later strands every passkey made. In a browser the api then sets the same session cookie.
A new deviceSigning in on a device or a browser the member has not used before sends a push to their other devices and a card in their chat: "New sign-in to MyPaisa: an iPad, with Google, today at 19:41. Was this you?", with Yes, it was me and No, sign it out (which signs that device out). Until the member answers, Members and devices shows it as not confirmed, and the owner's chat gets one line with Open Admin center (MA-102, MA-76).
On the deviceTokens live in the Keychain, this device only, readable after first unlock. Access tokens last five minutes and are refreshed in the background with the refresh token, which rotates on use. Each signed-in iPhone or iPad is a Device row with its name, model, last seen and push token.
Every callThe api's authorizer checks the access token, the member's status and session epoch on every HTTP call and when a stream opens, and the open stream checks them again every 60 seconds (§21.5). Sign out everywhere and pause use Cognito's own calls (AdminUserGlobalSignOut, AdminDisableUser) together with the member's session epoch, so they take effect on the next request (MA-102); signing out one device deletes its Device row and revokes its refresh token.

The second check (MA-76, MA-102). Some actions need proof that the member is holding the device now: the owner's admin actions (§9.3), from the Admin center or the admin's chat (§20.3), an import's Confirm and rolling an import back (§18.5, §22.2), leaving the household (MA-172), approving a new kind (propose_kind, §4.8; Arun, 26 Oct 2026, MA-197: a kind changes what every member can register), and nothing else. A bank or card statement sent for the budget is routine, not an import, so it needs no second check (§4.9); the Excel history importer keeps it. Plan items and saved Projection assumptions change a plan, not the records, and need none either (§6.6). The app asks the api for a challenge bound to that action, then gets a fresh assertion: Sign in with Apple again (iOS shows a Face ID sheet), or, where the member has added one, a passkey (Face ID); a member who signs in only with Google signs in with Google again. In the web app it is a passkey or a fresh Apple or Google sign-in in the browser. The api accepts the action only with an assertion under five minutes old whose nonce is that challenge. The app's own Face ID lock (MA-171) is a local comfort and never authorises anything on the server.

Joining. The owner taps Invite in the Admin center (or types /invite, optionally /invite viewer). The api makes a one-time link, https://dashboard.mypaisapp.com/join/<token> (dashboard-dev for dev), single use, 24-hour expiry, bound to this household and that role, and the owner sends it with iOS's share sheet. The invitee opens it on their own iPhone: the link opens MyPaisa (or a page saying where to get it, MA-73), shows the invite ("Arun invited you to the Dutta household"), and their Sign in with Apple or Google creates their member and Cognito user; then the three setup questions. The owner removes a member from Members and devices in the Admin center.

More than one way in (MA-77). A member can add a second sign-in, Apple or Google, or a passkey, from You: already signed in, they complete the new provider's sign-in, and the api links that sub to their Cognito user. sub is the key and the address is for display, so a renamed account still works and an address handed to someone else does not. The owner can unlink a member's sign-in from the Admin center; unlinking signs that account out everywhere. Every link, unlink and sign-in is an audit row. Leaving the household (MA-172) deletes the member's Cognito user and revokes Apple's and Google's tokens (Apple's through its REST endpoint, signed with the environment's Sign in with Apple key from SSM); their accounts and history stay with the household.

Roles.

RoleCan
ownerInvite and remove members, register and correct any member's records, set the household budget and settings, see every member's detail, and alone add plan items and save the Projection's assumptions (§6.6). The owner is the household's one admin (Arun, 25 Oct 2026: "there is only 1 admin"): the only person who sees the Admin center, the agents' requests in the chat and the admin desk
memberRegister, correct and close their own records (anything new in the chat, an editable figure in place, §4.10); see the household overview; see their own detail; view the Projection and ask what-ifs, saving nothing; opt in to sharing their detail with the household
viewerRead the household overview and whatever members share; nothing else

Views. The Portfolio card and Home have a switch: Household (every account, every member, one total) and Me (my accounts). The owner, and any member whose detail is shared, appear as further tabs. A member's brief covers their own accounts plus one household line; the owner's brief covers the household with a line per member. Alerts go to whoever owns the account, and to the owner as well if the owner asks.

Isolation. Every item is keyed by the household, every tool call carries the calling member as a principal, and the registry layer refuses a read or write outside that member's rights. One DynamoDB table cannot enforce that with IAM alone, so it is enforced in code and covered by tests ("member A can never read household B; a member cannot read another member's detail unless shared"). Each member's chat memory, decisions, preferences and cooldowns are their own. The monthly Claude ceiling is the household's (§15.1), and no member may spend more than their share of it (60% by default), so one chatty member cannot spend the household's allowance.

Scope. Two members in one household is personal software. Several unrelated households using an app that says "ADD, 64% confidence" starts to look like investment advice to the public, which is regulated in the UK. The model supports more households; using it that way is a separate decision about wording and scope, not a technical one.
