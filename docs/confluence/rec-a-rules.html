1. The two rules, and two more

  1. Claude never produces a number. Every figure comes from code with tests. Claude chooses what to say and how to say it.
  2. The app gives no calls and cannot trade. No broker login, no orders, and no buy, sell or hold call: nothing it shows or says tells the household to buy, add, hold, pause, trim or sell (MA-307).
  3. The layman sees the summary; the detail is one tap away. Every message has a plain top and a technical underside. Nothing technical is shown unasked.
  4. Only admins write, through one write service. Adding anything (a record, an event, a kind, a plan item) and deleting it happen only in the chat: a card, a Confirm tap, an audit row, and for a delete the second check too (MA-309). An existing figure that its kind marks editable (a value, a rate, a date, an amount, an assumption) is corrected in the chat, or in place on any screen, at either door: tap it, type the new value, see the before and after, Save. Nothing is added or deleted in place. Only an admin adds, corrects or deletes; every other member views only, their own preferences aside (§4.5, MA-308). Every path runs through one write service, which validates the change against the kind and writes it with its audit row (§4.10). Arun, 24 Oct 2026: "Dashboard will be read only (except for admin)"; widened on 26 Oct 2026 (MA-186): "The UI should only allow editing existing figures by hand, no creation"; and on 2 Nov 2026 (MA-307): "Even Deletion will have to go throw AI chat. Only admins can do all these. Others users can view only." The Admin center's exception stays: it acts on admin settings and operations, never on a record, each behind the second check and an audit row (§4.5, §8.3).

3. System context

Page 1 of the Lucid architecture (open): the household's doors on the left (the iOS app and the web app), the chat path along the top (API Gateway, the chat api, the updates queue, the agent, the outbox, the sender, the SSE stream on the api host back to both doors, and Apple push and Web Push), sign-in below it, the background jobs, the stores, and the failure path to the admin's email. The other six pages zoom into one part each and are drawn in their sections.

One container image and a handful of handlers: api (a FastAPI app wrapped in Mangum for the chat routes, the data routes, the one correction route and the owner's admin routes, MA-265, MA-266), agent, sender, worker (which runs each background job by its type: the price ingest that values holdings, documents, check-ins, the nightly views and Projection runs), stream (the SSE stream on the api host, a FastAPI app on Uvicorn as a separate build target of the same Dockerfile through the Lambda Web Adapter 1.1, §19.5, MA-266), the authorizer and the Cognito triggers. Nothing waits on anything else directly: your messages, MyPaisa's replies and every background job travel through SQS queues that retry them and keep what still fails (§19). The agent Lambda is the only one that talks to you in the chat, and the sender the only one that delivers to the doors: it appends to each member's stream log, which the stream sends to every open door, and sends Apple push and Web Push to a device with no open stream. The api Lambda, with the stream beside it on the same host, is the only one the doors call: its chat routes put what you send on the updates queue, and apart from those, the correction route (PATCH /v1/records/{id}, only from an admin and only for figures a kind marks editable, through the write service, §4.10) and the admin actions in the Admin center (§8.3: the security actions, the ceiling and caps, replays, agents' requests and settings, incidents), each admin action behind the second check, it can only read. Dev and prod are two copies of all of this (§17). Every other Lambda produces data they read, and every one of them writes a RunRecord saying what it did (§9).
