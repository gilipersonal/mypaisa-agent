22. Caching and memory for every agent (MA-285)

Arun, 29 Oct 2026: "I want automatic caching and memory enabled for all agents that will be built". Every agent calls Claude through one runner (AnthropicAgentRunner, MA-271, §7), so both come from the runner, once, and an agent gets them by being built on it: no agent's own code adds a cache mark or a memory store. Each agent's manifest (MA-246, §21.5) says only what differs: its cache lifetime and the memory scopes it may read and write.

22.1 The prompt cache: on for every call, checked on every change

The runner builds every request in one order, frozen per agent version, and marks it for the cache, so a call pays full price only for what changed since the last one. The rules follow from the cache being a prefix match: any byte that changes ends the cache at that point.

  • One order. Tools, sorted by name and serialised deterministically, then the system prompt, then the messages. Nothing that changes per member, per day or per request comes before the first breakpoint: no date, no member's name, no id, no figure, no unsorted JSON, no tool added for one member.
  • Dynamic context after the cache. Today's date, the member's name, role and mode, privacy mode and the spend ladder's step reach the model as a mid-conversation system message, after the cached prefix (Sonnet 5.5, Opus 5.5 and Haiku 5.5 take one with no beta header). It is also the operator's own channel, which a member's text cannot forge.
  • Breakpoints. At most three explicit breakpoints, one per stable layer: the tools and system prompt together, the household's layer, then the conversation notes (§7). The request's top-level automatic caching (cache_control on the request) takes the conversation's tail, the fourth of the four slots the API allows. A one-shot call with no history keeps the first breakpoint alone.
  • A lifetime per route, named in the agent's manifest from how far apart its calls start: under five minutes takes the 5-minute cache, which every call refreshes; five to sixty minutes takes the hour, whose write costs twice the input price against a tenth for each read; a longer gap takes neither and pays one cold call. The chat's fixed part takes the hour, since household messages come minutes apart (§7), and its tail five minutes; a daily or monthly run (the tuner's monthly note, the agent team's runs) takes five minutes within the run. A longer lifetime always sits before a shorter one.
  • One model per loop. A cache belongs to one model, so a loop never changes model mid-run; a cheaper step (a Haiku filter, a summary) is its own call. Effort and thinking settings are pinned per route for the same reason.
  • Batches and server tools. The overnight judges (§21.4) mark their shared instructions in every batch item; a hit inside a batch is likely, not certain. A web search or fetch call adds its own cache write after its results, which is expected.
  • No warming. The household's traffic is light, so no call is sent only to fill the cache; the first message of the hour pays the write. This is revisited if a first message's time to the first token passes its budget (§9.4).
  • The size floor. A prefix under 512 tokens (on the 5.5 models) is never cached and costs nothing extra; a manifest whose fixed part is that small says so rather than marking it.

Checked, because a broken cache fails silently. Requests keep succeeding and only the bill grows, so caching is tested where it can break:

  1. A unit test builds every agent's request twice (two members, two days, two runs) and asserts the bytes before the first breakpoint are identical; a manifest with no lifetime, or more than three explicit breakpoints, fails the build.
  2. T1 (§21.3) sends each changed agent's request twice in the evals workspace and expects cache_read_input_tokens above zero on the second.
  3. Every RunRecord keeps each call's cache read and write tokens (§9.1); the model panel shows the cache-read share per agent, and an alarm fires once when an agent's share leaves its band for a day (MA-233).
  4. In dev, cache diagnostics (beta cache-diagnosis-2026-04-07, on the Anthropic API only) names where a broken prefix first differs.
  5. The Console's caching analytics for each workspace (dev, prod and the evals) is the second place to look; each workspace has its own cache, so a prompt shared across them is cached once in each.

22.2 Memory notes: what an agent may keep

Every agent gets Claude's memory tool (memory_20250818) from the runner. Its six commands (view, create, str_replace, insert, delete, rename) work on a /memories directory that is MyPaisa's own store, not a disk: each file is a MemoryNote row in the one table (§4.1). A note holds plain words about the person or the work:

  • what a member asked MyPaisa to keep in mind ("remember that I am saving for a car next year"), how they like answers, what they are planning or waiting for;
  • for the agent team (phase 13): what it tried, what worked, a source's quirks, why the admin approved or rejected a request (§18.3, MA-289).

What a note never holds.

  • A figure or a record. No amount, balance, rate, percentage, date of a payment, account or card number, id, token or secret: the write handler refuses each in code, with the reason. A note may name a record ("the car loan"), and the agent looks its figures up with the tools when it needs them. The figure check (§21.2) matches a reply's figures only against the run's tool results and the member's own words, so a figure from a note cannot reach a reply even if one were written.
  • A setting. "Asha asked for fewer pings" may be a note; changing her ping budget is still her settings card. A note never changes behaviour on its own (§18.2).
  • Another member's detail. A member's notes hold only what that member said or did.

  • Through the policy gate. Each command is checked like any tool call (§21.2): the scope is in the agent's manifest, the path is the member's own or the household's, and the run is under its limits. It fails closed.
  • Read as data, at the cached price. The runner loads a run's notes once, at its start, into the notes layer under the third breakpoint (§22.1), labelled with their source and never as an instruction, so every later message of the conversation reads them from the cache. A note written during a run applies from the next run, which keeps the history append-only and the prefix unbroken; view stays for a note outside that set.
  • Untrusted text writes nothing. A run that has read untrusted text (a file, a statement, a fetched page; §21.2) cannot write memory: the gate refuses every writing command in it, delete included, so a poisoned page can neither plant a note nor erase one.
  • Seen and audited. Every write is an audit row (memory.write, the path, the run) and one line in Activity, "MyPaisa noted: ...". In You, What MyPaisa remembers lists the member's own notes and the household's, each corrected in place (a before and after with Save, via: inline_edit) or forgotten with a Confirm; nothing is added there, since a new note comes only from the chat (MA-288, §4.10). Forgetting removes the note's text for good and keeps its audit row without it.
  • Kept small. Each scope has a cap (§22.6), so reading it stays cheap; the agent tidies its notes with str_replace, and a write past the cap is refused with the reason.
  • For how long. A member's notes go when the member forgets them or leaves the household (MA-172 deletes them); the household's and the agent's stay until corrected or cleared.

Settled by Arun, 29 Oct 2026, on MA-287 and MA-288 ("go for all recommended options, I need the app to grow and remember me. But it should not exceed costs"): a member's notes are read only in that member's own runs, the owner included, who reads only the household's; a note is kept until the member forgets it or leaves the household, with no expiry; and the agent writes notes on its own, each shown in Activity as it is written, as well as when a member says "remember". The cost half is §22.6.

22.4 The agent team's notes (phase 13)

Each agent of §18.1 keeps its own self notes: the data steward a source's quirks and outages, the grader and tuner why each proposal was approved or rejected (so a rejected request is not proposed again within its setting's period), the ops warden each incident and the fix that worked, the admin desk how the admins like requests batched. A run reads them first. A note never changes behaviour: that is a setting inside its band, or a change request the admin approves (§18.2, §18.3). The Admin center lists each agent's notes for the admins to read, correct or clear, behind the second check with an audit row (MA-289).

22.5 Within a run: kept lean, never edited

The 5.5 models tie their thinking to the conversation as it was sent, so a stored history is never edited or trimmed (§7). Two things keep a run small without editing it:

  • A long tool run (an ops repair, a long import) uses server-side context editing (clear_tool_uses_20250919, beta context-management-2025-06-27): the API drops old tool results from what the model reads, and the history as sent is unchanged, so it is not an edit.
  • A long conversation starts afresh from a summary past about 50,000 tokens (§7), the plain shape that replays no earlier turn or thinking; it costs one cold cache, once.

Server-side compaction (beta compact-2026-01-12) is not needed at these sizes and is not used.

22.6 Within the budget

Arun, 29 Oct 2026: "it should not exceed costs". Caching lowers the bill, and memory is held inside the same ceiling, ladder and guards as every other call (§14.1):

  • Caching pays for itself. A cache read costs a tenth of the input price on Sonnet 5.5 and Haiku 5.5 ($0.20 against $2 a million tokens on Sonnet) and a twentieth on Opus 5.5; the hour's write costs twice the input price, once. The cache-read share's alarm (§22.1) catches a change that would quietly raise the bill.
  • Notes ride the cache. Loaded once into the cached notes layer (§22.3), a member's notes cost about half a penny to write at a conversation's start and about a twentieth of a penny a message after it, at Sonnet 5.5's prices and $1.30 to £1, beside the 1.5p to 3p a message costs (§7).
  • Hard caps. At most 2,000 tokens of a member's notes for one agent, 1,000 of the household's and 3,000 of an agent's own; at most two note writes in a run, each counted in the run's eight-call guard (§14.1). A write past a cap is refused with the reason, and the agent tidies instead.
  • Counted. Every memory read and write is costed into the cycle's SpendMonth under its own feature, memory, and the model panel shows it beside the rest.
  • On the ladder. From the 85% step (savers), the agent writes a note only when a member asks it to remember; from the 95% step it reads notes and writes none; at 100% Claude stops and the notes wait unchanged. Notes are never dropped to save money: reading them cached is the cheapest part of a conversation.
