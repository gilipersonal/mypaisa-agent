5. Data layer

5.1 Price sources: one plugin per feed, a chain per kind, chosen by configuration

Every feed is a plugin behind one small contract, and which plugins run, in which order, is configuration per environment. Yahoo Finance (yfinance, free, no key) is the default everywhere and the only feed local development needs. Switching to EODHD is a setting plus a key in SSM, not a code change, and it is a last resort: free sources first (yfinance, Twelve Data's free tier, free websites where their terms allow), EODHD only when the data steward shows a free source cannot serve a holding and an admin approves (§18.3). Prices exist only to value the household's holdings (MA-307).

The contract. A plugin implements:

class PriceSource(Protocol):
    name: str                                   # "yfinance" · "eodhd" · "twelvedata" · "issuer_page" · "ft" · "screenshot"
    def supports(self, instrument: Instrument) -> bool: ...
    def daily_bars(self, instrument: Instrument, since: date) -> Bars: ...   # native currency, with source, fetched_at, provisional
    def latest(self, instrument: Instrument) -> Quote | None: ...
    def fx(self, pair: str, since: date) -> Rates | None: ...                 # optional

Each plugin owns its own identifiers on the instrument (identifiers holds the Yahoo symbol, the EODHD code, the Twelve Data symbol and the ISIN side by side), its key in SSM (/mypaisa-agent/<env>/<plugin>/api_key), its rate limit, its GBX-to-GBP normalisation, its freshness rule, and its recorded fixtures. The ingest job sees only Bars, never a vendor shape. A plugin that is not in any chain is never imported, so a missing key is not an error.

Chains by configuration. The chain per kind lives in each environment's Terraform root (infra/dev/terraform.tfvars, infra/prod/terraform.tfvars) and reaches the Lambdas as one environment variable, with a per-instrument override in Instrument.price_sources[] for the odd case:

# infra/dev/terraform.tfvars (local uses the same shape from a .env file)
price_chains = {
  oeic      = ["yfinance", "issuer_page", "ft", "screenshot"]
  lse_etf   = ["yfinance", "twelvedata", "issuer_page", "stale"]
  us_etf    = ["twelvedata", "yfinance", "stale"]
  cash      = ["ecb", "twelvedata"]
}
# infra/prod/terraform.tfvars, once EODHD is chosen: put it first and add its key
#   lse_etf = ["eodhd", "yfinance", "twelvedata", "issuer_page", "stale"]
#   us_etf  = ["twelvedata", "eodhd", "yfinance", "stale"]

The first plugin that answers with fresh data wins, and the valuation records which one did. stale is the last entry everywhere: the previous close, labelled, never silently reused.

Proving a plugin. Every plugin passes the same contract test suite on recorded responses: the same instrument and date range give the same Bars shape, pounds not pence, the stale rule, idempotence per date, and a clean failure when the vendor is down. Tests never touch the network; a deliberate command refreshes the recordings. When two plugins are configured for the same instrument the ingest job records both, and the Activity page (§8.3) shows where they disagree (a close more than 0.2% apart, a missing day, a late correction). That report is how the "free first, EODHD if London closes prove unreliable" decision of phase 5 is made with numbers rather than impressions.

Twelve Data's free tier (8 credits a minute, 800 a day) is used for everything it serves: first in the chain for the US lines and the FX fallback, and second for London and Frankfurt closes from day one. Whether the free tier actually returns LSE and Xetra bars is not known; the chain simply skips a plugin that answers nothing, and the source-comparison report shows what it served. If it does serve them, EODHD is unnecessary. The daily credit budget is enforced in the plugin: the ingest job spends at most 200 a day, so the agent's own calls (symbol search on demand) never run the tier dry.

Input hygiene: drop interpolated bars, append today's close only when the session has traded, and mark a series STALE when its last bar is older than the previous session, so a value from it is labelled stale. Every job is idempotent per date.

5.2 Look-through

From the factsheet (and later the product page): asset allocation, top holdings, regional and currency split, shown on a holding's screen as what it holds. It feeds no engine and makes no call (MA-307). Refreshed when a new factsheet is uploaded or monthly from the page.

5.3 FX, calendars, time

GBP base; USD, EUR and INR, all published daily by the ECB. Each member can read every figure in any of four currencies, GBP, INR, USD or EUR (Arun, 29 Oct 2026, MA-275: "The app should support 4 currencies"); the stored value is always both the native amount and its GBP equivalent on the day, and a rupee figure is grouped in lakh and crore. The household's records are in the UK and India today; a record in the US or the euro area is added the same way when one is needed: a country is data (its kinds, its inflation and wage-growth priors, §6), not code. Money typed in one currency for a holding in another is checked and converted as in §4.7. Exchange calendars XLON, XETR, XNYS. All schedules in Europe/London.
