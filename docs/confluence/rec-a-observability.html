9. Observability: what the agent did, what it cost, and one trace from the door to the model

Arun, 26 Oct 2026 (MA-230): "I need AWS monitoring, tracing and Observability for LLMs and all components. Do whatever is best and tell me what can be done for end to end traceability across apps and agents. Application will do audits, anyway." The audit of what changed stays the app's (§4.6); this section is how everything else is watched, from the first run: every Lambda, both doors, the queues, every model call, and from phase 13 the agent team.

Three readers, three surfaces, one source of truth. Activity is built in phase 1 at both doors (MA-196), before the first record, so each layer can be followed run by run as it is built: each run's trigger and steps, the tools it called, what it proposed, its tokens and its cost.

One rule joins the three surfaces: every run has one run_id and one trace id, and both are on every log line, every span, every metric line, the RunRecord and the envelope of everything the run sends to a door. Whichever surface you start from, the same id opens the others.

9.1 The source of truth: the RunRecord

Every Lambda, not only the agent, writes one row per run when it finishes, success or failure (§4.1): the trigger, start and end, the trace_id, the build and the alias version that ran, every model call with its model, its input, output, cache-read and cache-write tokens, the cost computed from the price table, its latency and time to the first token, its stop reason and whether it refused or fell back to the template; every tool call with its duration, outcome, error class and the sizes of its input and output; what was sent to whom; the outcome; and the error if there was one. The agent also keeps the inputs and outputs of each tool call, truncated, so "why did it say that" has an answer: the row in the household's own table is the only place that content is kept outside ChatTurn, read through the api by role, and never copied to CloudWatch (§9.9). Its checks hold what the guards decided and what the member did next, the online evals' first reading (§21.4). Token counts come from the API's own usage fields, so the cost shown is what will be billed, reconciled weekly against the Anthropic Console (§14.1). Rows expire after ninety days. An alarm is a row of trigger alarm and a release a row of trigger deploy, so Activity lists both beside the runs.

9.3 Instrumentation: OpenTelemetry on every Lambda

  • One standard. Traces are OpenTelemetry. The AWS Lambda Layer for OpenTelemetry (the Application Signals build of the AWS Distro for OpenTelemetry, Python) is unzipped into /opt in the container image, because a container image cannot attach a layer, and every function runs with AWS_LAMBDA_EXEC_WRAPPER=/opt/otel-instrument, active tracing on, OTEL_SERVICE_NAME set to its handler (mypaisa-<env>-api, -agent, -sender, -worker, -stream) and OTEL_RESOURCE_ATTRIBUTES carrying env, build and version. Spans go to X-Ray's OTLP endpoint and, with Transaction Search on, every span is kept in the aws/spans log group with W3C ids. At this volume there is no reason to sample, so nothing is: the one trace a month you need is never the one that was dropped.
  • Powertools stays for Logger, Metrics (the embedded metric format), idempotency and parameters. Its Tracer is not used: it is a wrapper on the X-Ray SDK, two tracers in one process trace twice, and the X-Ray SDK knows nothing of the GenAI conventions. The log formatter adds the OpenTelemetry trace_id and span_id to every line, so Transaction Search and Application Signals join the logs to the trace.
  • Cold start. The layer enables only the AWS SDK, FastAPI (opentelemetry-instrumentation-fastapi on api and stream, MA-266) and HTTP instrumentations by default, which is all the handlers need (FastAPI; boto3; httpx to the Anthropic API and to APNs). The api is the latency-sensitive function: MA-232 measures its cold start with the layer and keeps it under 300 ms [verify]; if it cannot, the api keeps those instrumentations and nothing more.
  • The doors carry no SDK. A traceparent is sixteen random bytes and a version byte; each door makes one per action and sends it. What the door observed goes through POST /v1/telemetry (MA-234), a route of the api like any other, authorised the same way: no CloudWatch RUM script, no identity pool for it, no third party.
  • The local stack (§17.1) exports spans to the console, or into memory for tests. The leak test (MA-232): a recorded conversation with figures, names and a statement replays on the local stack, and no span attribute, span name, log line or metric line holds a prompt, a reply, an amount, a name, a token or an account number. It runs in CI with the other gates, and the smoke test after each dev deploy asserts one trace from api to sender through the X-Ray API (§17.4).

9.4 Model and tool spans: what Claude did, in the open conventions

Every call to the Anthropic API goes through one wrapper (MA-233) that opens a span named chat <model> and sets:

  • the OpenTelemetry GenAI conventions (Development status as of October 2026, with the Anthropic page's cache attributes): gen_ai.provider.name anthropic, gen_ai.operation.name, gen_ai.request.model, gen_ai.response.model, gen_ai.request.max_tokens, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, the cache read and cache write token counts, gen_ai.response.finish_reasons, and gen_ai.tool.name on each tool span;
  • MyPaisa's own: mypaisa.cost_usd (from the price table, the same figure the meter adds, §14.1), mypaisa.feature (chat, extraction, statements, search, notes, reviews, memory, evals), mypaisa.agent (§18.1), mypaisa.step (the ladder's step at the time), mypaisa.cache_hit, mypaisa.ttft_ms, mypaisa.refusal, mypaisa.fallback (the plain template went out instead), mypaisa.batch for Batches, and run_id, member and conversation_id;
  • never the prompt, the reply, a figure, a name or a document. Dev alone may capture the prompt and the reply on the span, behind a setting that prod refuses, so CloudWatch's trace explorer shows the synthetic household's conversations in full while nothing of the real one leaves DynamoDB.

Each tool call is a span tool <name> with its duration, outcome, error class and the sizes of its input and output; the truncated input and output stay on the RunRecord (§9.1). The server-side web search and fetch appear as what the API reports of them: their count and their cost.

With these attributes the spans appear as they are in CloudWatch's generative AI observability (generally available since October 2025, at no charge beyond the telemetry it reads: model invocations, tokens, tool calls, latency and errors, per agent) and in CloudWatch Omni's trace, session and topology views (September 2026): the same spans read through the newer console when it is wanted, and nothing is sent twice.

Quality is read from what members did, not from the model's word for it: proposals confirmed against cancelled, a question asked twice, refusals, template fallbacks, tool errors and the per-run self-audit's repeats (§7). They are metrics (§9.5). The online evals (§21.4) read the same signals from each run's checks and judge the flagged runs and a sample overnight.

Three counts of one thing. The meter's weekly reconciliation against the Console (§14.1) also checks the spans' token totals against the SpendMonth row: the API's usage, the meter and the spans must agree to the token.

9.6 Alarms, and who hears them

  • an error or a throttle in any function; the api's 5xx, or its p95 over 2 s for fifteen minutes;
  • a queue's oldest message over five minutes; any dead-letter queue holding anything (§19.3);
  • the dead man's switch, anchored to what the household is promised each day: at 07:45 when the views and the Projection run (after the night's price ingest) were not current by 07:00, or the day's check-ins (§4.9) and the insight job's findings (§10.1) are not queued; and when a check-in due that day has not been sent by 09:00 outside the admin's quiet hours (a check-in held by quiet hours is not late). Any schedule ten minutes late;
  • each step of the Claude ladder and the daily guard (§14.1), and a day's cost past the guard;
  • refusals or template fallbacks above 5% of calls in an hour; a tool's p95 over 10 s; no model call in an hour that had messages;
  • any holding's price older than two days; the audit chain failing its weekly check;
  • a burst of rejected api calls (401 and 403 over twenty in five minutes, with the access log saying from where); refused sign-ins over ten in five minutes;
  • any stream resync; push failures over five in an hour; a door's first word p95 over 5 s for an hour; any crash in prod;
  • the AWS cap's steps (§14.2) and the AWS Budgets backstop; and the watching itself: the aws/spans log group's ingestion over 1 GB a day, so observability can never run away;
  • from phase 13, a silent heartbeat (§9.8).

Routes. Every alarm goes to mypaisa-<env>-admin-alerts (SNS, the admin's email) from phase 0 (MA-231). From phase 1 an alarm is also a RunRecord of trigger alarm and a message on the owner's outbox (MA-29), so it reaches the chat and push; phase 10 makes it a card with its own push rules (MA-61), and phase 8's alert router adds quiet hours, cooldowns, the digest and the Replay button on a dead-letter alarm (§14.2, MA-137, MA-145). The composite alarm mypaisa-<env>-unhealthy (any function error, any dead-letter depth, the api's 5xx) is what pages the owner when something large breaks, one message rather than ten; the money and data alarms page on their own. Every alarm has an OK action, so the chat also says when it is over.

What phase 0 builds (MA-231). The alarms above that need no code: errors and throttles for each function, each queue's age and dead-letter depth, the api's 5xx and latency, the composite and the aws/spans ingestion alarm, in infra/modules/mypaisa/observability.tf, keyed on the fixed names of §9.3 and §19.2 so they stand before the things they watch (an alarm on a metric with no data waits, treated as fine). The api's two appear when the story that makes the API passes its id to the module (MA-30). The AWS Budgets backstop still emails the admin from infra/bootstrap; its route through the topic joins with the cap's steps, which act on it (MA-137). The rest need code and come with their stories.

9.8 The agent team (phase 13)

The daily run is one Step Functions execution with tracing on; each state's Lambda continues its trace, and an event on mypaisa-<env>-events carries the header to its consumer, so one day's run is one trace from the tick to the last job's write, and each agent is a service of its own on the map (OTEL_SERVICE_NAME per agent, named as §18.1 names it) beside the concierge's chat traces. The ops warden's replay starts a new trace linked to the original; an Incident row carries the trace id and the run ids it covers; every agent's heartbeat is a metric, and a silent one is an alarm as well as an incident (§18.4). The tuner's month grades and proposals are already RunRecord and audit rows; the trace adds how long each step took and what it cost (MA-235).

9.9 Privacy, retention and cost

Never in CloudWatch: a prompt, a reply, a figure, a name, an account number, a token, a file, a push payload's plain line. Member ids are hashed on every line and span; API Gateway's access log has no bodies. Content lives in the household's own table (ChatTurn, RunRecord, §4.1) under the app's roles; dev's synthetic household may be captured in full behind a setting prod refuses (§9.4). The leak test holds the line in CI (§9.3).

Kept for: logs 14 days; spans 30 days (aws/spans); metrics as CloudWatch keeps them, 15 months at no charge; RunRecord rows 90 days; the release's record for good in GitHub.

One account, one owner. Transaction Search (the X-Ray destination, its indexing rule, the logs policy for aws/spans) and Application Signals' discovery are one setting per account and region, and dev and prod share the account, so switching them on in dev switched them on for prod: dev's root owns them, with the aws/spans log group and its ingestion alarm, and prod's spans ride on them (Arun, 24 Nov 2026, MA-231). Prod sends no span until its first Lambda. aws/spans is one log group for both environments, so dev's roles can read prod's spans in it: they hold ids, hashes, durations and the attributes of §9.4, never a prompt, a reply, a figure or a name.

Rules. Dev first: Transaction Search and Application Signals were switched on from dev on 24 Nov 2026 (MA-231), their first month of dev is measured, and the figure is put to Arun before the first release that ships a Lambda to prod (MA-347; .claude/rules/aws-changes.md). An ingestion alarm on aws/spans (§9.6). Observability that costs more than the thing it watches has failed: about £4.50 of watching, both environments, against £9 to £32 of Claude.

The probe. Until the real images land (MA-237), dev runs one throwaway Lambda, mypaisa-dev-probe, a zip with the same OpenTelemetry layer (version 35 of the Application Signals build), the same environment and the same role policies the module hands every function, and a live alias the release moves. It proved the tower on 24 Nov 2026: its calls in Application Signals and as spans in aws/spans within five minutes, and a forced error through its alarm and the composite to the topic. It goes when the first real function ships (MA-347) (Arun, 24 Nov 2026, MA-231).
