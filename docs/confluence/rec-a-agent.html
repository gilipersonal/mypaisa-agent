7. The agent

One Claude tool loop (Sonnet 5.5 for chat and cards, Haiku 5.5 for small turns, statement lines and summaries), written as a thin explicit Python loop (AnthropicAgentRunner, MA-271) directly on the anthropic SDK and Pydantic v2 (@tool with a typed RunContext, inspired by PydanticAI, rather than LangGraph or CrewAI; docs/RESEARCH.md §6.3, MA-265), with strict tools over the registry and the wealth engine, through the Anthropic API with the key in SSM. Prompt caching on the system prompt, the tool list and the card rubrics; every agent's caching and memory come from this runner (§22). Anthropic's server-side web search and web fetch (with citations) look up a holding's public details when it is added (its ISIN, its listing, its fund house's page), in a call of their own that holds a holding's name and ISIN but no household figure (§21.2); the overnight eval judges go through the Message Batches API at half price (§21.4). Refusal or error falls back to the plain template.

It asks before it acts, and asks when it is unsure. The agent behaves like a careful assistant rather than a form. When a request is missing something it needs, it asks for that one thing, with buttons when the answer is from a short list (which holding, bought or sold, today or yesterday) and a typed reply otherwise. It never asks for what it can look up, and it skips every question the sentence already answered: "I put £200 into Balanced today" goes straight to the Confirm card. Every write is an admin's and is shown before it is saved; for any other member the agent answers and shows, and offers nothing to Confirm (§1, rule 4). A change that touches several records, such as closing an account and its holdings, is first proposed as a plan with one Confirm, then carried out step by step, each step audited. The one change to the records that starts outside the chat is an admin's correction in place: it shows its before and after with Save, and goes through the same write service (§4.10).

Registering anything by talking (§4.8). Whatever the kind, a sentence, a screenshot or a statement becomes a draft: draft_record or draft_event passes each field as a name and the member's own text, and code parses, types, derives and says what is missing. The agent asks for that, one thing at a time with chips, then shows a Confirm card with the figures code computed. A draft is saved only by Confirm.

It asks on its own account, through commitments and check-ins (§4.9). Code decides, with no LLM, when an EMI, a card bill, a SIP, a premium, a salary, a maturity or a valuation is due, and puts the check-in card on the outbox. The card shows exactly what a tap writes, so its Paid is the Confirm, with Undo; Different amount and Paid off in full open a short flow. On the 1st a check-in closes last month's budget, asking only for what no statement covered. These replace the first-of-the-month question and the 35-day nudge for a valuation. The agent still asks, when two members hold the same thing, whether a joint record is meant.

Statements are categorised (§4.9). Each line of a bank or card statement is matched against the merchant memory first; Haiku categorises the merchants it has not seen, and its answers join the memory once the member confirms the review card. Transfers, card payments and EMIs are recognised by code.

The mechanics are the ask_user tool, which ends the turn with a question and its buttons, and a PendingAction row per open flow, keyed by flow id, that records what MyPaisa is waiting for; the next message or tap from that member resumes its flow, and a day of silence clears it.

Chat memory: keep it all, send little (MA-115). Every message is kept, one ChatTurn row each, for ninety days; only the current conversation is sent to Claude. A conversation ends after thirty minutes of silence or when a guided flow finishes, but stays open while MyPaisa waits on an ask_user answer (up to the PendingAction's day). A new conversation starts from the fixed part (system prompt, tools, card rubrics; cached with the one-hour TTL, since household messages often come more than five minutes apart) and a few one-line notes on the member's recent conversations, written by Haiku when each one closed. The notes come after the cached part, so both members share one cached copy of it. Nothing else from old chats is sent: the agent looks up what it needs (get_audit, get_portfolio, get_networth), as it never asks for what it can look up. A conversation that passes about 50,000 tokens starts afresh from a summary. Re-sending whole histories would cost 7p to 85p a message after a month and keep growing; this way a message costs about 1.5p to 3p on Sonnet.

Two rules the loop keeps, from the API as it is now. History is append-only: each response's content is stored exactly as returned and an earlier turn is never edited or trimmed, because the 5.5 models tie their thinking to the conversation and an edited history is refused on newer accounts; a conversation is shortened only by starting a new one. And no tool call is forced: tool_choice stays auto (forcing one is an error on Sonnet 5.5 and Opus 5.5), tools are strict: true, and the prompt says which tool to use.

A per-run self-audit lists what MyPaisa told the member this week, so it does not repeat itself.

Tools: get_portfolio, get_holding(id), get_history(id, days), web_search and web_fetch (Anthropic's server tools), extract_document(s3_key, schema), propose_change(entity, patch) (saved only after an admin's Confirm), chart_series(id, days) (the series a card's chart is drawn from), ask_user(question, options[]) (ends the turn with a question; the answer resumes it through PendingAction) and get_audit(filter) (what changed, for "what did I change last week?"); and memory (Claude's memory tool, on MyPaisa's own store, within the scopes its manifest grants, §22). For the household's records (§4.8): list_kinds and describe_kind (what can be registered, and a kind's fields); draft_record(kind, fields) and draft_event(record, type, fields) (each field a name and the member's own text; code parses and types every value against the spec, derives what it can, such as the EMI, the maturity and the end date, and returns what is missing or uncertain; the draft is hashed in PendingAction, and Confirm commits exactly that draft; a delete or a restore is an event of its own, drafted the same way, that also needs the second check, MA-309); get_networth(view), get_commitments(window) and get_budget(month) (reading the views); query_ledger and query_ledger_sql (questions over the ledger: the structured one first, MA-62, and SQL on the read-only copy for the rest, §11.1); get_spend (what the cycle has spent, reported, never changed, §14.1); run_projection(overrides) (a what-if through a typed override, never saved, §6). Every tool that drafts or proposes a write (draft_record, draft_event, propose_change and the three below) is an admin's, enforced in code, not in the prompt (MA-308); and, for an admin, propose_kind (a new kind, or a new field on one, from the templates, approved behind the second check and versioned), propose_plan_item (a future change for the Projection: a new flow, a change to an existing flow, or an event on a record, returning what is missing and the engine's impact, saved only after the admin's Confirm) and rearrange_budget (the options code works out to cover a shortfall, each applied only on an admin's Confirm, §6).

Guardrails in code, not prompt: no tool can trade, spend beyond a search query, erase data, or message anyone but the member it is answering. A draft tool writes nothing: only an admin's Confirm, a check-in's tap or a Save in place commits, through the write service (§4.10). The monthly Claude ceiling with its ladder and guards (§14.1), the weekly red budget and quiet hours are enforced by the agent Lambda. /pause sets a flag every scheduled run checks first. These are the first layer of §21.2: every call of our own tools also passes a policy gate in code against the agent's manifest, third-party text reaches the model only as labelled data, a conversation that has read it loses every tool that sends data out, and every figure a reply states is checked against the tool results and the member's own words; §21 holds the guardrails and the evals that test them on every change.
