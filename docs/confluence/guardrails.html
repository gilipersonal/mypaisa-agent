The agents will keep changing: new kinds of holding (§4.8), new tools, new prompts, a new model every so often, and in phase 18 a team of agents that proposes changes to its own rules (§20). So nothing here is a list of tests written once. It is a set of rules every new piece must meet, checked by code.

23.1 The rules

  1. Guard in code, not in the prompt. What an agent cannot do is enforced where the prompt cannot reach: the tools it is given, a policy gate before every tool call, the one write service behind Confirm (§4.10), and checks on what it says before it is sent. The prompt explains; code decides (§1, §8).
  2. Test on change, never on a calendar. Claude model ids are pinned snapshots, so the agent behaves the same until we change a prompt, a tool, a guard, a kind or the model id. The golden set runs on the pull request that makes such a change, and before a model change reaches prod; it never runs on a timer, where it would only measure noise.
  3. Check every live run with code, judge a few. What changes without a pull request is what members ask and send. Every run is checked by code at no cost; every flagged run and a random 10% are judged overnight; only a rate that leaves its band raises an alert.
  4. People calibrate the judges. A model that grades a model is trusted only as far as it agrees with the admin's own reading: monthly, and whenever a judge, a prompt, a tool or the model changes.
  5. Nothing new ships without its cases (the growth rule). Every agent, tool, prompt and kind is declared in one manifest, and CI refuses one with no safety case and no capability case. Every incident, and every finding of a review, becomes a case the same day.

23.3 Offline evals: gated on change, never on a calendar

A case is a task on the synthetic household (the one figure set the dev seed and the boards use, MA-110): a conversation or an event, the records it starts from, and what must be true afterwards. Its graders come in order of trust: code first, on the outcome (the PendingAction draft's values, the records after Confirm, nothing written before Confirm, every figure grounded, the tools called and not called); a binary judge only for what code cannot measure ("asked one thing at a time", "plain and clear"), one judge per failure mode, with an "unknown" answer allowed. Each case carries its tags: the agent, the tool, the kind, the flow, the story key and its suite. Cases are Inspect AI datasets in evals/; Inspect runs the trials, scores them and keeps the logs.

Three suites.

SuiteHoldsPasses when
safetyRed-team cases: injection in a file, a page or a merchant name; a request beyond the member's role; a trade, tax advice, another household, "sell everything"Every case passes every trial (pass^k)
regressionGraduated capability cases, every incident and review finding, the kinds' generated casesThe pass rate stays at or above its baseline less its measured noise, reported with its standard error

Unit tests still never reach the Anthropic API (TECH_STACK §6): T1 and T2 are an eval job of their own, on dev's key, not the test suite.

Non-determinism. A case runs several trials; safety needs every one, regression is compared as a paired difference with its standard error, and a gap smaller than the measured noise is not a regression. A flaky case is read by a person (the transcript, not only the score) and either fixed or moved to capability.

23.4 Online evals: every run checked by code, a few judged

Every run, at no cost. The RunRecord's checks (§10.1) hold the gate's decisions, the figure check, a refusal, a template fallback, tool errors, the loop's length and its cost; and the member's own signals: a proposal cancelled, a correction within seven days of a Confirm on the same record, a question asked twice in a conversation. Any of these flags the run.

Judged overnight. Every flagged run and a random 10% of the rest are judged by the same binary judges as T1, on Haiku through the Batches API at half price. The random share is there to find what no flag catches. Each verdict is an EvalResult row (§4.1) beside the run. Nothing leaves the AWS account: the judges are Claude calls from our own Lambda, and no evaluation service sees the household's money.

Alerts on rates, not on flags. The same job counts each rate (guard trips, figure misses, member signals, judge fails) and compares it with its band over the last eight weeks. Only a rate outside its band raises an alert, through the alert router (§15.2); the rest is a line in the weekly digest. No CloudWatch metric is added: the rates live in the EvalResult rows and the runs.

Advisory until calibrated. Until the admin's calibration lands in phase 8 (MA-255), the judges' verdicts go to the digest only and never alert.

23.5 Calibration and growth

The admin calibrates the judges (MA-255), in the Admin center, monthly and whenever a judge, a prompt, a tool or the model changes, or flags spike. About 30 runs are offered: every run where a judge and a code check disagree, flagged runs and a random share, each with its transcript, its tool calls and the verdicts. The admin marks pass or fail for each failure mode, with a one-line critique. Each judge's true-positive and true-negative rates are measured on labels it was not built from; a judge below 0.8 on either drops to advisory until a pull request fixes it. The labels (EvalLabel, §4.1) are the judges' ground truth.

A real failure becomes a permanent case. A run the admin marks as failed is rewritten onto the synthetic household (its figures, names and files replaced, its shape kept), shown to the admin, and on Confirm becomes a regression case through a pull request. The same goes for every incident and every finding of a review, the same day.

One manifest (MA-246) declares every agent (its model route and its tools) and every tool: its side effect (read, draft, commit through Confirm, external), the roles that may call it, its household scope, whether untrusted text removes it, its per-run limit and its eval tags. The policy gate reads it at run time; the coverage check reads it in CI and fails a tool, agent, prompt file or kind template with no safety case and no capability case; §8's Tools list is checked against it.

Kinds bring their own cases (MA-254). Each kind template's field spec generates draft cases (varied phrasings, both currencies, dates in several forms, a missing field), graded by code. Approving a new kind or field runs its cases in dev first and shows the result before Confirm.

The team's changes carry their evidence (MA-256). Each agent of §20 has its own manifest entry and safety suite. A ChangeRequest that changes a prompt, a rule, a threshold or a model carries the affected suites' T1 results from dev; a failing safety case blocks its approval.

Each phase ends with a read. A phase whose stories touch an agent ends with a person reading 30 of its new runs and naming their failure modes; a new mode becomes a code check, a judge or a case before the next phase starts. Cases that always pass and judges that never fail are retired or moved to T2 only.
