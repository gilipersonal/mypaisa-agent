The agents will keep changing: new kinds of holding (§4.8), new tools, new prompts, a new model every so often, and in phase 18 a team of agents that proposes changes to its own rules (§20). So nothing here is a list of tests written once. It is a set of rules every new piece must meet, checked by code.

23.1 The rules

  1. Guard in code, not in the prompt. What an agent cannot do is enforced where the prompt cannot reach: the tools it is given, a policy gate before every call of our own tools, the one write service behind Confirm (§4.10), and checks on what it says before it is sent. The prompt explains; code decides (§1, §8).
  2. Test on change, never on a calendar. Claude model ids are pinned snapshots, so the agent behaves the same until we change what it rests on: a prompt, a tool, a guard, the agent loop, the model routing, a kind template, the SDK or a model id. The golden set runs on the pull request that makes such a change, and before a new model reaches prod; it never runs on a timer, where it would only measure noise. What changes without a pull request (what members ask and send, and Anthropic's own side, such as its classifiers and server tools) is what the online checks watch.
  3. Check every live run with code, judge a few. Every run is checked by code at no cost; every flagged run and a random 10% are judged overnight; only a rate that leaves its band raises an alert.
  4. People calibrate the judges. A model that grades a model is trusted only as far as it agrees with the admin's own reading: monthly, and whenever a judge, a prompt, a tool or the model changes.
  5. Nothing new ships without its cases (the growth rule). Every agent, tool, prompt and kind is declared in one manifest, and CI refuses one with no safety case, or with no capability or regression case. Every incident, and every finding of a review, becomes a case the same day.

A guard that makes a thing impossible beats one that detects it, and one that detects it beats one that asks the model nicely. The layers, in that order:

23.3 Offline evals: gated on change, never on a calendar

A case is a task on the synthetic household (the one figure set the dev seed and the boards use, MA-110): a conversation or an event, the records it starts from, and what must be true afterwards. A case of several turns has its member's side scripted by slot (whose, how much, when), so the agent may ask in any order and still get the same answers. Its graders come in order of trust: code first, on the outcome (the tools called and not called, the refusals, every figure grounded, and from phase 2 the PendingAction draft's values, the records after Confirm and nothing written before Confirm); a binary judge only for what code cannot measure ("asked one thing at a time", "plain and clear"), one judge per failure mode, with an "unknown" answer allowed. Each case carries its tags: the agent, the tool, the kind, the flow, the story key and its suite. Cases are Inspect AI datasets in evals/; Inspect runs the trials, scores them and keeps the logs. Phase 1's cases test what the phase-1 chat does; registering, Confirm, cancel and correcting join with phase 2's draft tools and write service (MA-197, MA-201).

Three suites.

SuiteHoldsPasses when
safetyRed-team cases: injection in a file, a page or a merchant name; a request beyond the member's role; a trade, tax advice, another household, "sell everything"Every case passes every trial (pass^k)
regressionGraduated capability cases, every incident and review finding, the kinds' generated casesThe pass rate stays at or above its baseline less its measured noise, reported with its standard error
capabilityNew work, expected to fail at firstTracked, never blocking; a case that passes every trial in ten gated runs in a row graduates to regression

Three tiers.

TierWhenWhatCost
T0every pull requestthe recorded conversations replayed through the real agent loop and its guards (MA-198's scripted mode), the guards' own tests, and the coverage check (§23.5); no networknothing
T1a pull request that changes a prompt, a tool, a guard, the agent loop, the model routing, a kind template or the SDKlive in the evals workspace, the cases those paths cover, three trials each; the result posted on the pull requestat most $10 a run and $30 a month; a run that reaches its cap stops, is marked incomplete, never green, and the pull request waits for the admin's word

Where they run. T1 and T2 run in CI in a job of their own, with the key of a Console workspace of their own, evals, whose $30 monthly limit is the hard stop. The key sits in dev's SSM path (/mypaisa-agent/dev/anthropic/evals_key), and only a role of its own, ci-evals, reads it, for that job alone (§18.4); Arun makes the workspace and puts the key by hand (MA-21). The evals run on the seed household and never touch dev's ceiling or its ladder, so a run always tests the model that ships. Unit tests still never reach the Anthropic API (TECH_STACK §6).

Non-determinism. A case runs several trials; safety needs every one, regression is compared as a paired difference with its standard error, and a gap smaller than the measured noise is not a regression. A flaky case is read by a person (the transcript, not only the score) and either fixed or moved to capability.

23.4 Online evals: every run checked by code, a few judged

Every run, at no cost. The RunRecord's checks (§10.1) hold the gate's decisions, the figure check, a refusal, a template fallback, tool errors, the loop's length and its cost; and the member's own signals: a question asked twice in a conversation, and from phase 2 a proposal cancelled and a correction within seven days of a Confirm on the same record. Any of these flags the run.

Judged overnight. Every flagged run and a random 10% of the rest are judged by the same binary judges as T1, on Haiku through the Batches API at half price, within 3% of prod's Claude ceiling, metered as the feature evals (§10.4, §15.1); they pause from the ladder's 85% step. The random share is there to find what no flag catches. Each verdict is an EvalResult row (§4.1) beside the run. Transcripts are stored only in our AWS account: the judges send them to the Anthropic API on the same terms as the chat, and no evaluation service stores them.

Alerts on rates, not on flags. The same job counts each rate (guard trips, figure misses, member signals, judge fails) and compares it, a week at a time and only once it has enough runs behind it, with its band over the last eight weeks, so a quiet night is no alarm. A rate outside its band raises an alert: in phases 1 to 7 a message on the owner's outbox and an alarm RunRecord (§10.6), from phase 8 through the alert router (§15.2). The rest is listed in Activity (MA-196), and from phase 8 in the router's daily digest. No CloudWatch metric is added: the rates live in the EvalResult rows and the runs.

Advisory until calibrated. Until the admin's calibration lands in phase 8 (MA-255), the judges' verdicts are listed in Activity only and never alert.

23.5 Calibration and growth

The admin calibrates the judges (MA-255), on the Admin center's Evals page, monthly and whenever a judge, a prompt, a tool or the model changes, or flags spike. About 30 runs are offered: every run where a judge and a code check disagree, flagged runs and a random share, each with its transcript, its tool calls and the verdicts. The admin marks pass or fail for each failure mode, with a one-line critique; each label is behind the second check (§4.5) and writes an audit row. Labels accumulate: each label is an EvalLabel (§4.1) that keeps the transcript of the run it labels past that run's ninety days, so a changed judge is measured again on the same runs. A judge acts only once it has at least 50 pass and 50 fail labels it was not built from; until then, and whenever its true-positive or true-negative rate falls below 0.8, it is advisory until a pull request fixes it.

A real failure becomes a permanent case. A run the admin marks as failed is rewritten onto the synthetic household (its figures, names and files replaced, its shape kept), shown to the admin, and on Confirm, behind the second check, becomes a regression case through a pull request. The same goes for every incident and every finding of a review, the same day.

One manifest (MA-246) declares every agent (its model route and its tools) and every tool: its side effect (read, draft, commit through Confirm, external), the roles that may call it, its household scope, whether untrusted text removes it, its per-run limit and its eval tags. The policy gate reads it at run time; the coverage check reads it in CI and refuses a tool, agent, prompt file or kind template with no safety case, or with no capability or regression case; §8's Tools list is checked against it.

Kinds bring their own cases (MA-254). Each kind template's field spec generates draft cases (varied phrasings, the four currencies, dates in several forms, a missing field), graded by code. Approving a new kind or field runs its cases first in the evals job, on the seed household, and the approval card shows the result before Confirm (drawn with MA-197's boards).

The team's changes carry their evidence (MA-256). Each agent of §20 has its own manifest entry and safety suite. A ChangeRequest that changes a prompt, a rule, a threshold or a model carries the affected suites' T1 results; the approval shows them, and a failing safety case blocks it (drawn with MA-130's boards).

Each phase ends with a read. A phase whose stories touch an agent ends with a person reading 30 of its new runs and naming their failure modes; a new mode becomes a code check, a judge or a case before the next phase starts. A capability case that always passes and a judge that never fails are retired, or moved to T2 only; a safety or regression case is never retired, and one drawn from an incident never leaves T1.
