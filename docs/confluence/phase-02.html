The household's first records, registered by talking and shown at both doors, in a structure that grows without a migration (ARCHITECTURE.md §4). Anything new is created in the chat, with a card, Confirm and an audit row; an existing figure is corrected in place where it is shown; both go through one write service. The simplest kinds come first (savings, cash, a property's value, a pension's value), so the whole path is proved before the maths arrives.

  • One dynamic structure (MA-27, ARCHITECTURE.md §4.1). Kinds are data. Records are documents: Record {kind, kind_version, owners[{member, share_pct}], country, ccy, liquidity, status, parent_id?, instrument_id?, attrs{}}; an ISA account is a record and its funds are child records; Instrument stays the shared market reference. History is events: Event {record, type, effective_date, payload{}, source, actor, document_id?}, append-only, hash-chained with the audit log and never edited (a correction or a reversal is a new event); current state is the fold of its events through the kind's handlers. Figures are views: each record's value series, NetWorth, the budget month, commitments due and projection runs are materialised from events and rebuilt after a spec change, so the structure evolves with no migration. Account, Position, Liability and Transaction fold into Record and Event for the household's own records; there is no relational schema. Every item is keyed by the household and carries schema_version. A record ends as closed, matured or sold, never deleted.
  • Kind specs and the draft tools (MA-197, ARCHITECTURE.md §8). A versioned kind spec holds its fields (typed; required, optional or derived; editable or not), its valuation method, the events it accepts, its commitment and check-in templates, its dashboard grouping (class, liquidity, country) and how it is presented. The valuation methods and event handlers are a fixed, tested code library (last figure, accrual, amortising, revolving, market-priced, and the PPF, EPF, NPS, SGB and LIC schedules) that specs only combine. The tools: list_kinds, describe_kind, draft_record(kind, fields: [{name, text}]) and draft_event(record, type, fields); code parses and types every value against the spec, derives what it can, and returns what is missing or uncertain; the draft is hashed in PendingAction, and Confirm commits exactly that draft. The agent asks only what is missing, one thing at a time, with chips, and never asks what it can look up. With propose_kind (the admin only, enforced in code) the agent proposes a new kind from the templates ("Sukanya Samriddhi: accrual at its rate to 21 years"); the admin approves it behind the second check (Arun, 26 Oct 2026), and it is versioned. No screen, form or tool is added.
  • One write service, and correction in place (MA-201, ARCHITECTURE.md §1, §9.3). The chat's Confirm and an in-place correction go through one service: validated against the kind, written as an event, with its audit row. An existing figure that its kind marks editable (a value, a rate, a date, an amount, an assumption) is corrected where it is shown: tap it, type the new value, see the before and after, Save; the change is a correction event with its audit row (via: inline_edit). Nothing can be created in place. A member corrects their own records' figures and the admin anyone's.
  • The api's data routes (MA-74), behind phase 1's authorizer: each member gets only what they may see, the JSON limited to it, and PATCH /v1/records/{id} accepts a correction only to a figure the kind marks editable.
  • The audit log from day one (MA-28, MA-40, ARCHITECTURE.md §4.6): an AuditEvent row in the same transaction as every record change, hash-chained; get_audit and "what changed this week?" in the chat.
  • The first kinds (MA-203): savings, cash, a property's value and a pension's value, each registered from one sentence or a screenshot, for any member, with joint shares where there are two owners; a property asks for a new valuation every six months.
  • Owners and joint shares (MA-33): each member's records have their owners, and a joint record has two owners with their shares; each member registers their own, the admin can register for any member, and the card names the owner.
  • The chat's commands (MA-35): onboarding, add, update, privacy, pause, resume and help, typed or from their shortcut chips.
  • Guided flows (MA-39): with chips, for adding a record, logging an event, updating a valuation and changing a setting: one question per card, the same card edited in place, fields already given skipped; the ask_user tool and the PendingAction row with a day's expiry, holding several open flows keyed by flow id, so one flow arriving mid-way does not wipe another.
  • Reading a file (MA-37): the docs Lambda reads a factsheet PDF or a valuation screenshot sent from the camera, a scan, Photos or Files with Claude on the Anthropic API (structured outputs, citations, per-field confidence), and the Confirm / Edit / Cancel card adds or updates a record; nothing saved without Confirm.
  • Money in any currency (MA-156, ARCHITECTURE.md §4.7): every record keeps its currency from the Confirm card that added it; a parser in code reads £ $ € ₹, the codes, the words and lakh and crore; an amount in another currency than the record's is never saved as it is, and MyPaisa asks for the amount that arrived (the ECB-rate estimate joins in phase 3, with MA-44); the original amount, rate and source stay on the event.
  • The Confirm card and the Portfolio card, designed first (MA-34).
  • Cards open their screens (MA-80): each card opens its dashboard screen, and each screen's Ask opens the chat about it; a screen's Update opens the chat with the guided flow already started.
  • The first dashboard (MA-208, ARCHITECTURE.md §9.3): the net worth hero and the records by class and by member, at both doors, in the shell of phase 1; a confirmed change reaches every open door over the stream and the figures move; privacy mode hides every amount.

Tests: a property test that every write, from the chat or in place, produces exactly one event and one audit row, and the chain verifies; the views rebuilt from events matching the running views; a new kind and a new field added as data, with no migration; a fixture per kind; draft_record typing every value, deriving what it can and listing what is missing; Confirm committing exactly the hashed draft; every refusal of the write service (a figure the kind does not mark editable, another member's record); the Confirm state machine; an expired Confirm refused; the guided flows (resume after a day, expiry, skipping fields already given, two members mid-flow at once, two flows open for one member); extraction against three real factsheets and three screenshots (fixtures with expected JSON); the currency parser on every form (£ $ € ₹, codes, words, lakh and crore) and a rupee amount against a pound record never saved as pounds; schema migration on a v0 item; every data route against each role and member status; Playwright and XCUITest for the in-place edit; the iOS scroll bench at 120 Hz with no dropped frames.
