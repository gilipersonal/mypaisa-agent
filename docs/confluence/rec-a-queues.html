21. Queues: nothing lost, everything retried (MA-138)

Page 4: the three queues and their consumers, the idempotency records, the retry rules, and the failure path from the dead-letter queues to replay. Open it in Lucid. The SSE stream the sender delivers through is §21.5. Arun, 24 Oct 2026: "Add SQS, the system should be resilient and self heal with retries from Queues."

Every place where one part hands work to another goes through an SQS queue. A queue holds the work until it succeeds, retries it with backoff when it fails, and keeps it in a dead-letter queue when it has failed too often, so a bad minute at Apple's push service, at the Anthropic API or at a data source costs a delay, never a message or a day's work.

The chat api checks the member's token, queues the message and answers 202 at once, so the door never waits on the agent; the agent writes its words into the turn's buffer while it writes, which the stream sends to every open door, and the finished message goes through the outbox into the member's stream log, so nothing depends on a connection staying up: on opening, a door resumes from the last event it has (§21.5). Each member's messages are handled one at a time and in order, while members run in parallel; that keeps a guided flow and the append-only chat history (§8) in step. A card tap is acknowledged at once and its effect queued, so the button never spins. The scheduler puts jobs on the work queue (each schedule has its own retry policy and dead-letter queue), a finished job can queue the next (ingest, then engine, then brief), and from phase 18 the Step Functions run of §20.5 drives the same jobs.

21.2 Rules every consumer keeps

  • Idempotent. Every handler records what it has done (Powertools idempotency, keyed by the app's client id, the message id, or the job id and date), so a retry or a replay never does anything twice.
  • Backoff, not hammering. A failed message comes back after a growing wait; the work queue's maximum concurrency keeps yfinance, Twelve Data's free tier (8 calls a minute) and the other free sources inside their limits; reserved concurrency on the agent keeps Claude calls and spend in bounds (§15.1).
  • Fail fast on what cannot succeed. A malformed message, an unknown member or an instrument with no source goes straight to the dead-letter queue with its reason, instead of using up its tries.
  • Never silent. The brief, the wrap and alerts are always attempted; if their inputs are late they go out labelled stale.
  • Settings. Tries, backoff, concurrency and the replay limits are settings (§15.2, §20.2).

21.3 Dead-letter queues and replay

Each queue, and the scheduler, has a dead-letter queue. Messages stay there 14 days, SQS's limit, and a copy goes to raw/dlq/ in S3 for good. Each dead-letter queue has an alarm the moment it holds anything, which reaches the admin through the alert router (§15.2) as "failed work".

Replay moves dead-lettered messages back to their queue:

FromHow
Phase 1 (MA-139, MA-140)scripts/redrive.sh <queue>
Phase 8 (MA-137, MA-145)A Replay button on the alert, in the Admin center and in the admin's chat, behind the second check
Phase 18 (MA-135, MA-146)The ops warden replays on its own once the cause is healthy again, at most three times per message with growing gaps; a message that fails the same way again becomes an incident

Replays are safe: handlers are idempotent; a message more than an hour old is answered "still want this?" rather than acted on; and a Confirm tap whose PendingAction has expired is refused, so an old tap can never save a change by surprise.

21.4 Cost

SQS's free tier is a million requests a month. The household sends and receives a few thousand messages and jobs a month; the larger part is the Lambda service polling the three queues while they are empty, which counts as requests too. Dev's queue triggers are switched off while dev's schedules are, so the expected cost is nothing to about a dollar a month, measured in the first month and inside the AWS cap of §15.2. The dead-letter alarms cost a few pence each beyond CloudWatch's ten free alarms.

21.5 Live delivery over SSE

Since v4 (MA-186) both doors receive everything over one Server-Sent Events stream on the api host, which replaces v3's API Gateway WebSocket and its live host. The reply streams in as it is written; cards, check-ins and records.changed arrive on the same stream, so a check-in confirmed on the phone moves the laptop's dashboard. When no door is open, Apple push reaches the iOS app and Web Push the installed web app (§11). Built in phase 1 (MA-30), after a spike (MA-195).

  • The endpoint: GET api(-dev).mypaisapp.com/v1/stream, a route of the api's own REST API on its custom domain, so the web app's HttpOnly cookie and the authorizer reach it. The route's Lambda proxy integration is in the STREAM response transfer mode (API Gateway response streaming, since November 2025): up to 15 minutes per response, which the 14-minute cycle below fits, and a 5-minute idle timeout, which the 15-second heartbeat keeps open. The api is a REST API, not an HTTP API, because only REST APIs stream (MA-229).
  • The function: a Starlette app on Uvicorn behind the Lambda Web Adapter 1.1, with AWS_LWA_INVOKE_MODE=response_stream, built as its own target of the same Dockerfile, since the adapter would otherwise take over the other handlers (MA-229).
  • Order and resume: a per-member sequence counter and an event log, StreamEvent, kept at least seven days (§4.1). The sender appends each finished message, card, card edit, check-in and record change. A door resumes with Last-Event-ID, or ?after= after a reload, and gets everything after it, in order and never twice; a door further behind than the log gets resync and reloads.
  • Token deltas: the agent keeps a TurnBuffer per turn, updated about every 200 ms. The stream polls one small LiveHead item, every 200 ms during a turn and every 1 to 2 s when idle, and sends what is new.
  • Keeping it honest: a heartbeat every 15 s; the response ends at about 14 minutes with a retry, and the door reconnects from its last event.
  • Presence: each open stream keeps a Presence row fresh, in place of v3's Connection; push goes only to a device with no fresh presence.
  • Traceable: every event in the log and every push payload carries, in its envelope, the run_id and trace_id of the run that made it, so a door's "it arrived at 9:41:03" and the server's spans are one trace (§10.2, MA-232).
  • The clients: a fetch-based SSE client at both doors, not EventSource, so a 401 refreshes the token and reconnects. One leader tab per browser holds the stream for the others, and the stream closes 60 s after the page is hidden.
  • Sign-out lands at once: the stream re-checks the member's status and session epoch every 60 s and ends when either fails (MA-102, §4.5).
  • Cost: each open stream is a running Lambda, about $0.012 per open hour at 256 MB; the leader tab and the close when hidden keep it inside the free tier, and reserved concurrency of about 20 caps it (§15). The price is confirmed with Arun before apply.
  • The spike comes first (MA-195), as phase 1's first story. Its exit: the first delta at a browser and an iPhone in under 1 s, a correct resume after the connection is killed, and the cost per open hour measured. It writes its choice of route into this section.
