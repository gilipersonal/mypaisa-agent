MyPaisa architecture, v2

One Python agent on AWS Lambda that keeps the record of what the household holds, values it every day, works out its returns (XIRR and CAGR from the dated ledger), and talks to you through a private Telegram bot built for a layman. Python does the maths; Claude, through the Anthropic API, explains it, reads your factsheets and screenshots, and answers questions by calling the same code as tools. Everything is driven by the chat.

An early design record (v2, 23 Oct 2026): the Telegram bot and the £50 cap came before the app, the web app and the agent team. MA-307, 2 Nov 2026: the market side was retired; MyPaisa is a wealth tracker only.

How a message moves through the system

One Lambda does the thinking (agent λ). It wakes two ways: on a schedule, to value the holdings and send what is due, and on a webhook, when you message the bot or send it a file. Pick a scenario to watch the request travel.

    Why one agent Lambda and not three

    A check-in, an alert and a chat answer all need the same things: the holdings and their valuations, the dated ledger, your preferences, and the record of what the bot already told you. Putting them in one Lambda with one set of tools means a check-in and your 3 pm question are answered from the same facts. The webhook Lambda stays tiny on purpose: Telegram resends an update if it waits more than a few seconds, so it verifies the secret_token header, rejects any chat_id that isn't the household's, writes the update_id to DynamoDB so a retry is ignored, invokes the agent asynchronously and returns 200.

    How the agent thinks

    Claude never computes a number. Every figure comes back from a tool, and every tool is a Python function the scheduled pipeline also uses. Run the example to see one question answered end to end.

    The holdings registry: fed from the chat, generic by design

    An admin adds a holding by sending the bot its factsheet and a screenshot of the Monzo valuation, or by typing what it is. Claude reads the PDF and the image, fills a structured card with the source line for each figure and marks anything it is unsure of in amber, and nothing is saved until an admin taps Confirm. From then on the bot values it every day. Every holding is an Instrument with a kind, and a kind is a bundle of defaults (price chain, look-through source, how its value and returns are worked out), so a new ETF, a US or UK share, or a commodity adds a row of data, not code.

    Only admins write, and there can be several: the owner grants or takes back the role in the chat. Adding and deleting happen only in the chat; an admin corrects a figure in the chat or in place on a screen. A delete marks the record deleted: hidden from every view, restorable through the chat, its events, audit rows and files kept for good. Every other member views only.

    Three traps the example writes down. The ISIN is shared by the USD and GBP lines, so the listing is stored separately and the bot asks which line when the factsheet does not say. London GBP lines are often quoted in pence, so the price plugin normalises to pounds and a test guards the 100× error. And every holding here is a dollar asset in a sterling wrapper: one move in GBP/USD moves all of them, so the FX line on the Portfolio card is a portfolio-level item. The exchange calendars (XLON, XETR, XNYS) and ECB reference rates come free; the scheduler runs in Europe/London so the clock-change weeks take care of themselves.

    What you see in the chat

    A persistent keyboard with four buttons (Portfolio · Today · Ask · Settings), a menu of commands, and cards that are plain on top with a collapsed Technical details section underneath. Telegram's 2026 rich messages carry the table and the collapsible section; where they are unavailable the same card is HTML with a Technical button that edits the message in place. Every term in a technical section has a one-line glossary behind a tap. A read-only Mini App dashboard with interactive charts opens from the Portfolio card. Only admins see Correct and the add and delete flows; every other member sees the same cards, read only.

    Cost against the £50 cap

The key lives in SSM Parameter Store, read once per cold start, with a monthly spend limit set in the Anthropic Console as the hard stop. Figures at $1.30 to the pound.

    Its own codebase: mypaisa-agent

    A separate repository, its own Terraform state key and its own IAM role. One trap from the older wealth tracker's history: the OIDC subject claim embeds the repository's numeric id, so the new repo needs a trust policy with its id, not a copy of the old one's.

    Rules it inherits

    IAM only in Terraform, deploy by OIDC with a role pinned to this repository's own numeric id, no AWS keys anywhere, the Anthropic API key in SSM with a spend limit. Each function gets a small IAM role: one table, one bucket, its SSM path, its model ARNs. The bot holds no broker login and cannot trade. Nothing is saved without an admin's Confirm: only admins add, correct and delete, and every other member views only. Privacy mode hides £ amounts, since bot chats are not end-to-end encrypted.
