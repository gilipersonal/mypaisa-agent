Guarded in code. Tested on every change. Watched live.

MyPaisa's agents read your statements, answer your questions and, later, propose changes to their own rules. This page shows the fences that stop them doing what they must not, and the tests that check they still do what they should whenever something changes.

Why not test every day

The tests run when something changes, and the live chat is watched instead

Nothing the tests check changes overnight. The Claude model MyPaisa uses is a fixed version, and its instructions, tools and fences only change when someone changes them on purpose. Running the same tests every day would cost money, give the same score, and teach everyone to ignore the alarms.

So the tests run on the change itself, before it reaches you. What does change every day is what you and your family ask and send, and that is watched live, every run, by code.

Claude model ids are pinned snapshots, so behaviour changes only when a prompt, a tool, a guard, the agent loop, the model routing, a kind template, the SDK or a model id changes, and each of those arrives through a pull request. A scheduled rerun of an unchanged golden set measures sampling noise and breeds alert fatigue.

Offline evals are therefore gated on change (T0, T1, T2). What changes without a pull request, member traffic and Anthropic's own classifiers and server tools, is covered by online evals: code checks on every run and a judged sample overnight (§21.1, rule 2).

Guardrails, strongest first

Five fences between a request and anything it can do

A fence that makes a thing impossible beats one that spots it, and one that spots it beats asking the model nicely. Each request passes all five, in this order.

  • Least agency. There is no tool that can trade, erase data, read a secret or message anyone else. Nothing is saved until you tap Confirm; a delete is an admin's draft, saved only on Confirm and the second check, and only marks the record deleted.
  • The policy gate. Code checks every tool call before it runs.
  • Untrusted text. What is written in a file or a web page is read as data, never as an instruction.
  • What it says. Every figure in a reply must come from a tool or from your own words; out-of-scope asks get a plain refusal.
  • Limits. The monthly Claude ceiling, the per-run caps and /pause.
  • Least agency (§7, §4.10): no trade, erase, secret or cross-member message tool; drafts write nothing; a delete is an admin's draft, saved only on Confirm and the second check, and only marks the record deleted (MA-309); Confirm commits exactly the draft whose hash PendingAction holds; the SQL copy runs DuckDB read only, external access off, configuration locked, over the asker's views (§11.1); admin actions behind the second check.
  • Policy gate (MA-247): manifest, role and household scope, strict schema with amounts as the member's text, run caps, taint; fails closed.
  • Untrusted text (MA-253): third-party text only as a JSON-encoded, labelled tool result, or a labelled document or image block; a quarantined extractor with no tools returns strict JSON with each field's source line; a conversation that has read such text, with its notes and summaries, loses every outbound tool.
  • Output checks (MA-248, MA-249): figures grounded in the tool results and the member's words after normalising unit, currency and rounding; one regeneration, then the plain template; scope refusals; no remote images.
  • Limits (§14.1): the ceiling's ladder, member, day and run guards, the tool-call cap, /pause. Mapped to the OWASP LLM (2025) and Agentic (2026) top tens in §21.2.
The policy gate

Code checks every tool call before it runs, and refuses when in doubt

When the agent wants to use a tool, a small piece of code stands in the way and asks five questions. Is this agent allowed this tool? Is this person allowed it? Do the details make sense? Is the run inside its limits? Has this conversation read text from outside, such as a statement or a web page? If it has, every tool that could send something out is taken away for the rest of the conversation.

If the gate itself breaks or is slow, the answer is no.

Before every call of one of our own tools (MA-247): the tool is in the calling agent's manifest; the member's role and household scope allow it (§4.5); arguments match the strict schema and ranges, an amount being the member's own text parsed by code (§4.7), a typed override only taking minor units and an ISO 4217 code (§6); the run is under its tool-call cap and not repeating a call; and once untrusted text is in the conversation, tools whose side effect is external are removed for it and for every note or summary drawn from it.

It fails closed: an error or a timeout refuses. Each decision is a span attribute and an entry in RunRecord.checks. Anthropic's server tools (web_search, web_fetch) run inside one API request where no code can stop a call, so they are given only to a call holding no household figure (a name and ISIN, never an amount), with max_uses set.

Offline evals

Tested on the change, before it merges, never on a timer

The tests are about 40 short conversations with a pretend household, the same family the designs use. Most are marked by code: did the agent call the right tool, ask one thing at a time, refuse what it should, and state only figures it was given? A second Claude, a judge, marks only what code cannot, such as whether a reply was plain and clear.

Every change runs the free recorded tests. A change to anything the agent rests on also runs the live tests, three times each, because a model can answer differently each time. A new Claude model runs everything five times before it answers you.

Cases are Inspect AI datasets on the synthetic household (MA-110's figure set), graded by code first on the outcome: tools called and not called, refusals, grounded figures, and from phase 2 the PendingAction draft, the records after Confirm and nothing written before it. Binary judges only for what code cannot measure, one per failure mode, with "unknown" allowed. Multi-turn cases script the member's side by slot.

T0, every PR: recorded replays through the real loop and guards, guard tests, the coverage check; no network. T1, when a prompt, tool, guard, the agent loop, model routing, a kind template or the SDK changes: the affected cases live, three trials each, in the mypaisa-evals Console workspace, at most $10 a run and $30 a month; a run stopped by its cap is incomplete, never green. T2, on a model-id change: the full suite, five trials, and the release waits for it. Safety needs pass^k; regression is a paired difference with its standard error.

safety

Attempts to trick the agent: hidden instructions, asks beyond someone's role, trades, tax advice, "sell everything". Every attempt must fail, every time.Red-team cases: injection in a file, page or merchant name, role escalation, out-of-scope asks. Pass every trial (pass^k).

regression

Things that already work, every past mistake, and each kind of holding's own tests. They must keep working.Graduated capability cases, incidents and review findings, the kinds' generated cases. At or above baseline less measured noise, with its standard error.

capability

New things the agent is still learning. They are tracked, never block a change, and join the regression set once they pass reliably.Tracked, never blocking; graduates after passing every trial in ten gated runs in a row.

Online evals

Every live run checked by code; a few read overnight by a judge

Every real conversation is checked by code, for free: did a fence trip, was a figure unsupported, did someone cancel a proposal or correct a figure soon after confirming it, or ask the same question twice? Any of these flags the conversation.

Overnight, a judge reads every flagged conversation and one in ten of the rest, picked at random to catch what no flag notices. You only hear about it when a rate moves out of its normal range, never for a single flag. Transcripts are kept only in MyPaisa's own AWS account.

Each run's RunRecord.checks hold the gate's decisions, the figure check, refusal, template fallback, tool errors, loop length and cost, and member signals (a question asked twice; from phase 2, a cancelled proposal and a correction within seven days of a Confirm).

Nightly, every flagged run plus a random 10% are judged by the T1 judges on Haiku through the Batches API, within 3% of prod's ceiling, metered as the feature evals and pausing from the 85% step; verdicts are EvalResult rows. Each rate is compared a week at a time with its eight-week band; outside it, an alert goes to the owner's outbox (§9.6), through the alert router from phase 8. The rest is listed in Activity. Judges stay advisory until calibrated (MA-255). No CloudWatch metric is added.

The judges

A model that grades a model is trusted only as far as it agrees with you

Once a month, and whenever something changes, the Admin center shows you about 30 conversations. You mark each one pass or fail and add a line saying why. Each mark asks for your Face ID or passkey, like the other admin actions.

Your marks add up over time. A judge only counts once it has at least 50 of your passes and 50 of your fails to be measured against, and it stays a quiet helper until then. If it disagrees with you too often, it goes back to being a helper until it is fixed. A conversation you mark as failed is rewritten onto the pretend household and becomes a permanent test.

MA-255: the Evals page offers about 30 runs a month (every judge and code-check disagreement, flagged runs, a random share), and opens again on a change to a judge, prompt, tool or model and when flags spike. The admin labels pass or fail per failure mode with a critique, each label behind the second check with an audit row (Arun, 28 Oct 2026).

Labels accumulate as EvalLabel rows that keep their run's transcript past its ninety days. A judge acts only with at least 50 pass and 50 fail labels it was not built from; below 0.8 on its true-positive or true-negative rate it is advisory until a pull request fixes it. A failed run is rewritten onto the synthetic household and, on Confirm behind the second check, becomes a regression case through a pull request.

Growing with the agents

Nothing new ships without its tests

MyPaisa will keep gaining new tools, new kinds of holding and, later, a team of agents. Each one is written into a single list, the manifest, with the tests that prove it. A check refuses any change that adds something without its tests. Each new kind of holding writes its own tests from its fields, and a change the agent team proposes to its own rules shows you its test results before you approve it.

One manifest (MA-246) declares every agent (model route, tools) and every tool (side effect, roles, scope, whether untrusted text removes it, per-run limit, eval tags). The gate reads it at run time; the coverage check reads it in CI and refuses a tool, agent, prompt file or kind template with no safety case, or with no capability or regression case. Kind templates generate draft cases (MA-254); a ChangeRequest carries its suites' T1 results and a failing safety case blocks it (MA-256). Every incident and review finding becomes a case the same day; a safety or regression case is never retired.

The words

Terms, in plain words

Eval, case, trial
A test of the agent; one scripted conversation with what must be true afterwards; one attempt at it. A case runs several trials because a model can answer differently each time.
Golden set
The fixed collection of cases, about 40 for the chat, on the pretend household.
Judge
A second Claude that answers one yes-or-no question about a reply, such as "was it plain?", used only where code cannot check.
pass^k
Passing every one of k trials, not just one of them. Safety cases need it.
T0, T1, T2
The three tiers: recorded tests on every change; live tests when what the agent rests on changes; the full suite on a new model.
True-positive and true-negative rates
How often a judge agrees with you on the failures, and on the passes, counted apart so a rare failure is not hidden by many passes.
Untrusted text
Anything written by someone outside the chat: a statement, a factsheet, a web page, a shop's name.
Quarantined extractor
The step that reads a file. It has no tools at all, so whatever the file says, it can only fill in the form it was given.
Manifest
The one list of every agent and tool, what each may do, and the tests that prove it.
Second check
A fresh sign-in with Apple, Google or a passkey, under Face ID, that the server checks before an admin action; the app's own Face ID lock never authorises anything.
