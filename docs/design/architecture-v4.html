MyPaisa Agent · technical architecture · v4

From a tap at either door to Claude and back, on AWS, in one trace.

The household's wealth tracker end to end, driven by the chat: the iOS app and the web app, the AWS services between them, the concierge's tool loop on the Anthropic API, the six agents that keep the records, the budget and the wealth forecast current, and which Claude model each piece uses. Admins add, correct and delete through the chat; every other member views. The forecast comes from the household's actual numbers: XIRR and CAGR from the dated ledger, the Projection and the Budget forecast. Goals and the saving they need, what changed and why, scenarios side by side and a forecast range graded each month all come from code; a nightly insight job in the worker says what matters, quietly, in a Monday digest; and an admin can plan with Opus. Pick a journey below and press play to watch it move through the system.

    Observability

    One message is one trace, from the finger to the last word

    The door makes a W3C traceparent for each action. API Gateway, the api, SQS and every Lambda carry it on, so nothing in the path starts a trace of its own. Each model call is a span named chat <model> in the OpenTelemetry GenAI conventions, with MyPaisa's cost and ladder step beside it. Prompts, replies and figures never leave DynamoDB.     The concierge

    One Claude tool loop, with code doing every sum

    The agent Lambda runs one tool loop on Sonnet 5.5. Before each call it reads the month's spend and lets the ladder choose the model. When an admin starts plan with me, the session runs on Opus 5.5 in a loop of its own, since a loop never changes model. It sends only the current conversation after a cached prefix, loops through strict tools until it can answer, ask one thing, or show a Confirm card. Only an admin's turn can draft a change. A draft writes nothing: only a Confirm, a check-in's tap or a Save in place commits, through the one write service; a delete also takes the second check.

    Asks before it actsEvery write is shown before it is saved; a change across records is one plan with one Confirm, then audited step by step.
    Never asks what it can look up"I put £200 into Balanced today" goes straight to the Confirm card.
    Keeps it all, sends littleEvery turn kept 90 days; only the current conversation goes to Claude, about 1.5p to 3p a message on Sonnet.
    Falls back, never fails silentA refusal or an error sends the plain template, with code's numbers.

    The agent team · phase 13

    Six agents that never call each other

    Each agent is a Lambda with its own role, tools, model routing and budget share. They publish events on the mypaisa-<env>-events EventBridge bus and leave work in DynamoDB; the daily run is one Step Functions state machine. No agent can trade, read a secret, erase data or apply infrastructure. The concierge is the agent Lambda from phase 1, with the budget keeper's meter; the grader and tuner arrive in phase 9; the data steward, the ops warden and the admin desk join in phase 13. Together they keep the records, the budget and the wealth forecast current as the household's numbers change.

    Code decides, Claude explainsCode makes every number: XIRR, CAGR, the Projection and the Budget forecast. Claude tags, writes, asks and answers.

    Model routing

    Three Claude models, each where it earns its cost

    Sonnet carries the conversation, Haiku files and filters at volume, and Opus plans with an admin who asks for it, in a loop of its own. All three go through one wrapper that meters every call from the API's own usage counts, so the cost on the span is what will be billed. Prompt caching covers the system prompt, the tool list and the card rubrics. Prices are as TECH_STACK.md records them, per million tokens in and out.

    Where the data lives

    One table for state, one lake for the record, one store for secrets

    The household's records are data, not code: kinds are versioned documents, records are documents, their history is append-only events, and the dashboard reads materialised views. Every change and its audit row are written in one DynamoDB transaction, chained by hash. A delete marks the record deleted: hidden from every view, restorable through the chat, its events, audit rows and files kept for good.

    Guardrails

    Enforced in code, not in the prompt

    Claude never produces a number

    Every figure comes from tested code: XIRR, CAGR, loan schedules, the Projection and the Budget forecast, the goal solver, the attribution and the fan. Claude chooses what to say and how; the figure check holds every number, and the claim check every cause, to what a tool returned.

    §1 rule 1 · §6.2 · wealth/

    The app cannot trade

    No broker login and no orders, and nothing says buy or sell. A nudge, a digest or a plan card states facts and options, never "you should". No tool can trade, spend beyond a search, erase data or message anyone but the member it answers.

    §1 rule 2 · §7 guardrails

    A policy gate before every tool call

    Code checks the agent's manifest, the member's role and household, the arguments (an amount stays the member's own words) and the run's caps, and fails closed. Third-party text is data only; a chat that has read it loses its outbound tools, and the server tools run in a call with no household figure.

    §21.2 · MA-247, MA-253

    Tested on change, watched live

    T0 replays on every pull request; T1 live, three trials, when a prompt, tool, guard, loop, routing, kind or the SDK changes; T2 on a model change before release. Every live run checked by code; flagged runs and 10% judged overnight; judges calibrated by the admin. The explainer.

    §21.3 to §21.5 · MA-246, MA-250 to MA-255

    Only admins write, through one service

    Several admins; the owner grants or takes back the role in the chat. An admin adds and deletes only in the chat, with a card and a Confirm (a delete also takes the second check and marks the record deleted, restorable); a figure is corrected in the chat or in place with Save. Every other member views only. Each write validates against the kind and writes the audit row.

    §4.10 · PATCH /v1/records/{id} · MA-308, MA-309

    Admin actions take a second check

    A fresh, server-verified Sign in with Apple, passkey or Google, bound to the action. A local Face ID alone never authorises anything on the server.

    §4.5 · MA-76

    Nothing is lost

    Every hand-off is an SQS queue; handlers are idempotent; a dead letter alarms at once and replays safely. An old Confirm whose flow expired is refused.

    §19 · Powertools idempotency

    Nothing private in CloudWatch

    No prompt, reply, amount, name, token or account number on any span, log or metric; members are hashed. A leak test replays a conversation in CI to hold the line.
